# 無料版の門（FREE_LIMIT 200）と無料版の設計の矛盾 — 判断待ち V1.00（2026-09-11・V2.97時点）

> **裁定ずみ（2026-09-11・利用者「案Bで」）→ V3.00 で実装。** 門は「解いた数」ではなく「単元」で決める
> （必修は全部・他の単元の新規と模試の続きは有料版・触った問題の復習は止めない）。FREE_LIMIT は撤廃（定数だけ残す）。
> 詳細は DESIGN_DECISIONS「無料版の門は『解いた数』ではなく『単元』で決める（V3.00）」。下は裁定前の本文をそのまま残す。

§5-④「無料版の制限を実装」に入る前に、ここを決めないと二度手間になる。裁定は1つ（A／B／C のどれか）。

## 1. 何が矛盾しているか

| | いまの実装（V1.53・license.js） | 無料版の設計（2026-09-08） |
|---|---|---|
| 無料で解ける範囲 | **解いた問題 200問まで**（`FREE_LIMIT = 200`・`solved_ever` の高水位で数える）。超えると新規の出題が止まり、復習だけ続く | **過去問の必修は全部**（同梱249問）。「必修を人質に取っていない」ことを信用の柱にする |
| 模試 | ライセンスを見ない（解禁条件を満たせば誰でも全部受けられる） | プチ1回・ハーフ1回だけ（体験用の予想問題90問）。フル・いじわるは有料版 |
| 有料版 | 鍵（シリアル）で門が開く | 過去問1,197問＋予想問題＋フル・いじわる。データは配布JSON |

**このままだと、無料の利用者は必修249問を解き切れない**（200問で「無料でお試しいただける200問を解き終えました」が出る）。
設計の文言「必修は買わなくても最後まで使える」と画面が食い違う。

## 2. 案

### 案A：FREE_LIMIT を上げる（例：300）

- **やること**：`license.js` の定数1つ。文言の「200問」は `L.FREE_LIMIT` から出ているので自動で追従
- メリット：1行。テストは `test_batchAH`（無料枠）の数値を直すだけ
- デメリット：数が同梱シードの大きさに結びつく（必修が増えるたびに上げる）。画面は「お試し ○問」という**数の枷**の見せ方のまま。設計の「必修は人質に取らない」というメッセージにならない
- リスク：低。配布JSON（1,197問）を無料の人が入れても300問で止まる＝いまと同じ守り

### 案B：数ではなく「単元」で門を作る（推す）

- **無料で開く範囲**＝ 単元が **必修** の問題（出典を問わない）＋ 印つきの予想問題（`free_a`／`free_b`）。
  **それ以外の単元**の新規出題は鍵が無ければ止める。復習は止めない（V1.53 の原則）
- **やること**：
  1. `part1 startSession`：鍵が無いとき `options.freeUnits = ['必修']`（いまの `solvedOnly` と同じ渡し方。scheduler はライセンスを知らない・§7-B）
  2. `scheduler buildQueue`：`freeUnits` があれば、候補を「単元が freeUnits に入る」か「pool mock かつ印つき」か「全部の肢を解いたことがある（復習）」に絞る（`solvedOnly` の隣に1条件）
  3. `license.js gate()`：`locked` の意味を「200問超え」から「必修の外に手を伸ばした」へ。文言：「必修はこのまま全部使えます。他の単元と模試の続きは有料版です」
  4. 模試：鍵が無いとき プチ・ハーフは `exam_history` の回数が1以上なら設計 §3-2 の文言（結果は見せる）。フル・いじわるは解禁条件を満たしていてもカードを「有料版で」にする
  5. `FREE_LIMIT` は撤廃（定数は残してよいが門には使わない）。`test_batchAH` の無料枠の観点を単元の観点へ置き換える（観点は減らさない）
- メリット：設計をそのまま符号化。**数を持たない**ので必修が増えても直さない（§1-3「導けるものは持たない」）。
  無料の利用者から見て「必修は全部・他は有料」が一目で分かる。配布JSONが漏れても必修以外は開かない（守りは案Aと同等）
- デメリット：改修は5か所・テスト2件（新規1・置き換え1）。単元名「必修」の判定は既存の `isHissu()`（単元名に『必修』を含む）を使うので、分類キーの表記に依存する（いまは全部「必修」で統一されている・V1.98 の rankFor と同じ前提）
- リスク：中。`buildQueue` の候補絞りに条件を1つ足すので、有料（鍵あり）と無料の両方の道を run_all で通す必要がある。V2.96 と同じ手順で通せる

### 案C：門を撤廃し、配布（何を渡すか）だけで分ける

- **やること**：`solvedOnly` の門を外す（または常に paid 扱い）。模試の回数制限だけ実装
- メリット：学習側のコードから売り方の理屈が消える。いちばん単純
- デメリット：配布JSONが1本漏れたら全部開く。鍵が開くのは「フル・いじわる・模試2回目」だけになり、**鍵を買う理由が薄い**
- リスク：高（守りが無くなる）。§7-B「鍵の使い回しは防げない（承知のうえ）」よりさらに一段弱い

## 3. 推し：案B

理由は3つ。
1. 設計（2026-09-08 裁定）の文言と画面が一致する。案Aは数の枷の見せ方が残る
2. 数を持たないので、必修が増えても（第116回で+50問）門を直さない
3. 守りは案Aと同等で、案Cより強い

案Bの費用：改修5か所・新規テスト1件・既存テスト1件の観点置き換え・run_all 1回（約25分）・DESIGN_DECISIONS 1節。
V2.96 と同じ規模。1会話で終わる。

## 4. 裁定のあとに決めること（案Bのとき）

- 無料で開く単元を「必修」だけにするか、「必修＋人体の構造と機能」のように**体験の幅**を持たせるか（設計は必修だけ）
- 鍵が無い状態で **フル模試の解禁条件を満たした**ときのカードの見せ方（「有料版で受けられます」＋結果画面下の購入導線・設計 §3-3）
- 体験用の90問を**どう端末へ入れるか**：同梱シードに足す（SEED_VERSION を上げる。既存端末には onlyExisting なので届かない＝設定の「入れ直す」が要る）か、配布JSONとして別に渡すか

## 5. 決めないときに起きること

無料の利用者が必修200問を解いた時点で止まる。設計と画面が食い違ったまま公開が続く。
`FREE_LIMIT` の文言（「無料でお試しいただける200問」）は既に公開版に出ている。
